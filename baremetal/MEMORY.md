# Raspberry Pi 1 Bare-Metal 부팅 성공 핵심 가이드 (MEMORY.md)

이 문서는 Raspberry Pi 1 (ARMv6) 환경에서 Circle 프레임워크를 사용하여 SPC-1000 에뮬레이터를 베어메탈로 개발 및 빌드할 때, 정상적인 부팅(시스템 초기화 및 블루스크린 진입)을 보장하기 위해 반드시 준수해야 하는 핵심 제약 사항과 설계 원칙을 정리합니다.

---

## 1. C++ 전역 생성자 제약 (Global Constructors)

### ❌ 문제점
* 에뮬레이터 핵심 클래스(예: `Cassette`, `CScreenDevice` 등)를 전역 변수 영역에 직접 선언하면, 시스템 기동 시 컴파일러 런타임이 `.init_array` 영역에 기록된 전역 생성자들을 먼저 실행합니다.
* 이 시점은 아직 CPU MMU(메모리 관리 장치), 캐시 시스템, 메모리 시스템(`CMemorySystem`), 스택 포인터 등이 초기화되기 전이므로, 생성자 실행 도중 락업(Lockup) 또는 메모리 예외가 발생하여 기기가 묵묵부답인 상태(레인보우 화면)가 됩니다.

### ⭕ 해결책 및 원칙
* **전역 객체 선언 금지**: 에뮬레이션 관련 클래스 객체는 절대로 전역 변수로 인스턴스화하지 않습니다.
* **`CKernel` 멤버 변수 설계**: 모든 주변 장치 및 로더 클래스들은 `CKernel` 클래스의 내부 멤버 변수로 선언합니다.
* **동작 순서 제어**: 생성 및 초기화 시점을 `main()` 함수 진입 및 `CKernel` 생성 이후의 안전한 런타임 단계로 늦추어 해결합니다.

## 2. KERNEL_MAX_SIZE 경계 제한 (2MB Limit)

### ❌ 문제점
* Circle 라이브러리(`libcircle.a`)는 컴파일 시 커널의 최대 한계 크기(`KERNEL_MAX_SIZE`)를 기본적으로 **2MB (2 * MEGABYTE)**로 상정합니다.
* 부팅 극초기 단계(`sysinit.cpp`)에서 프로그램 바이너리 코드와 BSS 세그먼트(정적 버퍼 영역 등)의 전체 한계점(`_end`)을 검사하며, 이 값이 2MB 경계를 단 1바이트라도 침범하면 어떠한 경고도 출력하지 못하고 시스템을 무조건 멈추는 **`halt()`**를 호출합니다.
  * *예: 1MB 이상의 큰 크기의 정적 버퍼(`static char tape_buffer[1024*1024]`)를 선언하면 BSS 영역 팽창으로 인해 부팅이 즉각 차단됩니다.*

### ⭕ 해결책 및 원칙
* **정적 버퍼 크기 다이어트**: 파일 목록 배열이나 임시 버퍼는 SPC-1000 기기 스펙(64KB RAM)에 맞게 현실적인 용량(예: 테이프 버퍼 512KB, 임시 버퍼 64KB 수준)으로 압축하여 BSS 팽창을 방지합니다.
* **Circle 코어 라이브러리 재설정**: 필요 시 Circle 전체 빌드 설정을 4MB 수준으로 명시적으로 상향 재설정해야 합니다.
  ```bash
  cd /home/msx/circle
  ./configure -r 1 --kernel-max-size 4 -f
  ./makeall clean && ./makeall
  ```
  *(어플리케이션의 `Makefile`만 `KERNEL_MAX_SIZE=0x400000`로 수정하는 것으로는 해결되지 않으며, 이미 컴파일된 `libcircle.a` 코어 라이브러리도 반드시 함께 재컴파일되어야 동작합니다.)*

## 3. C++ 표준 라이브러리 (STDLIB_SUPPORT = 3) 사용 금지

### ❌ 문제점
* `STDLIB_SUPPORT = 3`을 선언하고 `<vector>`, `<string>`, `std::sort` 등의 C++ 표준 STL을 링킹하면 아래의 두 가지 치명적인 문제가 발생합니다.
  1. **초기 Heap 할당 예외**: C++ 표준 라이브러리 초기화 런타임이 기동 도중 `malloc`을 호출하지만, 이 시점에는 시스템 힙 할당자(`CMemorySystem`)가 가동되기 전이므로 Null 포인터 참조 크래시가 납니다.
  2. **ARMv6 미지원 명령어 실행**: GCC 툴체인의 `libstdc++.a`는 일반적으로 ARMv7-A(Raspberry Pi 2 이상) 타겟으로 범용 빌드되어 배포되는 경우가 많습니다. 원자적 동기화 명령어(`LDREX`, `STREX` 등)가 Raspberry Pi 1 CPU(ARMv6)에서 실행될 때 **정의되지 않은 명령어 예외(Undefined Instruction Exception)**가 발생하여 부팅이 멈춥니다.

### ⭕ 해결책 및 원칙
* **C-Style 고수**: Raspberry Pi 1 베어메탈 타겟 어플리케이션은 절대로 C++ STL 헤더를 쓰지 않아야 합니다.
* **순수 C 언어 메커니즘**: `std::vector`, `std::string` 대신 C 표준 고정 크기 정적 배열, 포인터, 그리고 `<string.h>`에서 제공하는 전통적인 문자열 함수와 순수 C 언어 기반의 탐색/정렬 루틴을 사용합니다.
* **STDLIB_SUPPORT 기본값 유지**: `Makefile`에서 `STDLIB_SUPPORT` 설정을 무리하게 `3`으로 상향하지 않고 기본 규격으로 빌드합니다.

## 4. malloc/free 오버라이드 금지 및 newlib 표준 힙 설계

### ❌ 문제점
* 압축 라이브러리(Bzip2, Miniz 등) 연동을 위해 `malloc`, `free`, `realloc` 등의 표준 함수를 파일 단에서 직접 재정의(Override)하고 이를 Circle 힙 시스템(`operator new`/`operator delete`)으로 포워딩하는 방식은 매우 위험합니다.
* 컴파일러 표준 런타임 혹은 외부 라이브러리 일부가 다른 위치에서 할당된 포인터를 저희가 재정의한 `free`로 전달하는 경우가 발생합니다. 이때 4바이트 크기 헤더 오프셋 불일치 등으로 인해 **Heap Corruption(메모리 오염) 및 초기 크래시**가 유발됩니다.

### ⭕ 해결책 및 원칙
* **커스텀 메모리 오버라이드 완전 배제**: `stub.cpp` 등에서 사용자 정의 `malloc`, `free`, `realloc`을 절대로 직접 구현하지 마십시오.
* **`_sbrk` 기반의 newlib 표준 힙 할당**: 
  * `malloc` 등의 동적 할당 요청은 GCC/newlib 컴파일러 라이브러리가 기본 내장한 표준 할당 시스템으로 완전히 일임합니다.
  * 표준 힙 할당자는 `stub.cpp`에 구현된 표준 시스템 콜인 `_sbrk`를 호출하여 BSS 세그먼트 끝(`_end`) 주소부터 힙 영역을 안전하게 위로 늘려가며 사용합니다.
* **Heap과 Stack의 안전 이격 설계**:
  * BSS 끝 / Heap 시작점: **약 1.92MB (`0x1ded40`)**에서 시작하여 위(Upward)로 성장
  * CPU 커널 스택(Stack): **4.15MB (`0x428000`)**에서 시작하여 아래(Downward)로 성장
  * 두 메모리 기둥 사이에 2.2MB 이상의 거대한 여유 공간이 영구적으로 확보되어, 부팅 및 에뮬레이션 가동 중 메모리 충돌이 원천 방지됩니다.

## 요약 체크리스트 (부팅 불가 시 자가진단)
1. **LED가 5번 깜빡인 뒤 무반응(레인보우 화면 유지)**: BSS 크기가 KERNEL_MAX_SIZE를 넘었는지(`_end` 주소 검사) 또는 C++ 전역 객체 생성자 혹은 메모리 오버라이드 오류가 있는지 확인하십시오.
2. **LED조차 깜빡이지 않음**: 하드웨어 접촉 불량(전원/HDMI)이거나 빌드에 사용되지 않는 클래스 링킹 중 극초기 크래시가 발생했는지 확인하십시오.
3. **`_end` 주소 진단 명령어**:
   ```bash
   arm-none-eabi-nm kernel.elf | grep " _end"
   ```
   출력 주소가 KERNEL_MAX_SIZE(4MB 설정 시 `0x408000`, 2MB 설정 시 `0x208000`) 한도 선 미만인지 반드시 검증하십시오.
